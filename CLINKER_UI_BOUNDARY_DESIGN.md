CSS, explicit component classes and semantic variables. Keep external style
dependencies out of the app. Preserve the current navigation and workflows.

## Ownership and scope

- Clinker owns the app bar, run form, file/project actions, tree and annotation
  import workflows, matching review, dialogs and application appearance preference.
- Clustermap owns its editor, selection toolbar, context menus and figure controls.
- Clinker supplies appearance tokens and controls component placement and size.
  It should not style library-owned buttons or query shadow roots for navigation.
- Keep annotation parsing and cluster matching in Clinker. This is a styling and
  integration refactor, not a redesign of the annotation data model.
- Retain New run as a visible button; File, Add data and Row order menus; Edit
  figure on the right; Theme and Help. Preserve the recent spacing and chevrons.

## Application CSS design

1. Introduce one application scope such as `.clinker-app` on the body or a root
   wrapper. Account for native dialogs and any body-mounted application UI.
2. Define semantic `--app-*` tokens for page, surface, subtle surface, foreground,
   muted text, border, hover, accent, focus, error and success. Include control
   metrics and typography where shared. Use contextual foreground/background
   pairs where contrast requires them, particularly primary actions.
3. Light and dark theme selectors should primarily assign token values. Define
   each component's structure and states once; avoid a second component system
   in a trailing dark-mode block.
4. Use explicit scoped classes for controls and variants, for example
   `.app-button`, `.app-button--primary`, `.app-menu__item`, `.app-field` and
   `.app-dialog`. Names are examples; choose a small consistent vocabulary.
5. Remove document-wide colour/border rules, universal dark-mode overrides and
   corrective `!important` declarations as their replacements land. Preserve
   intentional utilities such as `[hidden]` handling where justified.
6. Keep menu items borderless with hover and visible keyboard focus. Use borders
   for meaningful input and container boundaries; avoid borders on every nested
   section or action. Do not globally remove useful field boundaries.
7. Separate tokens, shared controls, component layout and responsive rules into
   readable sections or a few locally bundled files. No CSS tooling is required.
   If splitting files, update all packaging paths and avoid runtime remote imports.

## Theme and clustermap integration

Keep `auto`, `light` and `dark` preferences, existing persistence and system-change
handling. Resolve the preference once at the app level. Preserve accessible menu
state and labels. UI appearance changes must not modify the figure's theme,
annotation palettes, export background or saved figure configuration.

Use one explicit adapter at the plot/editor integration boundary:

```css
.clinker-plot-workspace {
  --cm-surface: var(--app-surface);
  --cm-foreground: var(--app-foreground);
  --cm-border: var(--app-border);
  --cm-hover: var(--app-hover);
  /* Map the remaining documented properties in this same adapter. */
}
```

The definitive property names and UI-mode API come from the clustermap handoff.
Its proposed contract includes `--cm-subtle`, `--cm-muted`, `--cm-accent`,
`--cm-focus-ring`, `--cm-font`, `--cm-control-height` and `--cm-control-radius`.
Do not assume those proposals are already implemented.

Ensure the editor and chart controls receive the adapter even if they occupy
different containers. Body-mounted library UI must be handled through the
upstream contract rather than global Clinker overrides.

After upgrading clustermap, remove app rules for library-owned component
internals, including selection-toolbar button/badge colours. Keep only placement
and sizing rules. Remove legacy `--clinker-*` theme hooks once migrated.

## Editor integration API

Replace Tree appearance's shadow-root traversal with the public section
navigation method supplied by clustermap. Let the editor handle tabs, filter
clearing, scroll and focus timing. Use its documented open/close events to keep
the Edit figure button and expanded state synchronised.

Preserve existing tree, annotation and selection editing entry points. Avoid
duplicating chart/editor state inside the app. Do not invent a dependency on an
upstream method before that method exists.
